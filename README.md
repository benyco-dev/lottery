# 로또 6/45 회차 통계

동행복권 로또 6/45 전 회차를 모아 **예측 가능성이 있는지 검정하고**, 없다는 결론 위에서
*사람들이 덜 고르는* 번호 조합을 추천하는 정적 사이트. 추천은 회차마다 기록되고 추첨 후 자동 채점된다.

> **당첨 확률은 올릴 수 없습니다.** 어떤 조합이든 1등은 8,145,060분의 1입니다.
> 이 사이트가 바꾸는 것은 확률이 아니라 **당첨됐을 때 몇 명과 나눠 갖는지**입니다.
> 환급률이 50%라 기대수익은 여전히 마이너스입니다. 재미로만 보세요.

## 1. 예측 가능성 검정 — 결론: 없음

`scripts/independence.py` 가 매주 7가지를 다시 검정한다 (본페로니 보정 α = 0.05/7 = 0.0071).

| 검정 | 관측 | 기대 | p |
| --- | ---: | ---: | ---: |
| 직전 회차 번호 재출현 | 1024 | 991.2 | 0.235 |
| 직전 보너스 → 이번 본번호 | 170 | 165.2 | 0.688 |
| 번호별 출현 균등성 (χ², df=44) | 29.6 | 44 | 0.952 |
| 번호쌍 동반출현 (MC B=1000) | 941.3 | 972.0 | 0.690 |
| 번호합 lag-1 자기상관 | 0.010 | 0 | 0.736 |
| 홀수개수 lag-1 자기상관 | 0.012 | 0 | 0.672 |
| 재출현 간격 평균 | 7.46 | 7.5 | 0.624 |

**전부 무의미하다.** 그래서 "핫넘버", "미출현 번호" 같은 것으로 다음 회차를 맞힐 수 없다.
사이트의 출현 빈도 통계는 관측용으로만 남겨두고 추천에는 쓰지 않는다.

카이제곱 적합도는 상단 꼬리만 본다. 양측으로 계산하면 χ²가 기대보다 *낮은*
(= 무작위보다 오히려 고르게 나온) 경우를 "유의"로 잘못 읽는다.

## 2. 번호 인기도 — 결론: 있음

당첨 확률과 달리, **1등 당첨자 수**는 번호에 따라 달라진다. 사람들의 선택이 균등하지 않기 때문이다.

측정 방법: 5개를 맞힌 티켓의 나머지 한 개가 보너스일 확률은 이론상 **1/39**로 고정이다(남은 39개 중 1개).
따라서 `w2 / (w2 + w3)` 가 1/39 보다 크면 그 회차 보너스 번호를 사람들이 더 많이 골랐다는 뜻이다.
회차별 지수의 **중앙값**을 쓴다 — 통합비율은 이상 회차 하나에 끌려간다
(1057회는 2등이 664명으로 평상시의 9배였고, 그 한 회차가 12번 지수를 1.05 → 1.47 로 올렸다).

| 구간 | 평균 인기지수 |
| --- | ---: |
| 1~12번 (생일의 '월') | 1.002 |
| 13~31번 (생일의 '일') | 0.986 |
| 32~45번 (생일에 없음) | 0.953 |

**독립 검증**: 2·3등 데이터로만 만든 이 지수가, 전혀 다른 변수인 1등 당첨자 수를 예측한다
(회차 본번호 6개의 평균 인기지수 vs 판매액 정규화 1등 당첨자 수, r = +0.109, p = 1.4e-4, n = 1226).

## 3. 추천 방식

* **가중치**: 인기지수의 역수 (`(1/index)^3`)
* **혼잡 필터**: 1~12번을 최대 2개까지만. 실제 회차에서 이 조건을 만족한 1024회는 위반한 202회보다
  1등 당첨자가 평균 **12.7% 적었다** (부트스트랩 95% CI +3.7~22.4%, 판매액 정규화)
* **구조 필터**: 번호합이 과거 80% 구간 안, 홀수 2~4개, 연속쌍 1쌍 이하, 10단위 구간 3개 이상 분산

매 회차 5세트를 만든다. 시드가 대상 회차 번호라 같은 코드로 누구나 같은 결과를 재현할 수 있고,
추천은 추첨 **전에** `site/data/predictions.json`에 커밋된다. 추첨 후 성적을 고쳐 쓸 수 없다.
과거 회차를 소급해서 기록에 넣지 않는다.

인기지수는 번호당 보너스 출현이 20회 넘게 쌓여야 안정되므로 **전체 이력**으로만 계산한다.
통계 탭의 5개 구간(전체 / 500 / 250 / 100 / 50회)은 관측용으로 그대로 남아 있다.

### 한계

* 효과 크기의 신뢰구간이 넓다(+3.7~22.4%). 여러 후보 제약을 비교한 뒤 고른 값이라 실제 효과는 하단에 가까울 수 있다.
* 자동선택(QuickPick) 비율만큼 효과가 희석된다.
* 인기지수는 회차당 보너스 1개에서만 나오므로 개별 번호 순위는 신뢰도가 낮다. 구간 경향이 더 믿을 만하다.

## 4. 채점

추첨 결과가 나오면 다음 실행에서 자동 채점한다. 1~3등이면 메인 상단에 당첨으로 표시하고,
낙첨이면 세트별로 몇 개 맞았는지 보여준다. 6개=1등, 5개+보너스=2등, 5개=3등, 4개=4등, 3개=5등.

## 5. 백테스트

`node scripts/backtest.mjs [회차수] [시드수]` — 과거 회차를 그 시점 데이터만으로 추천하고 채점한다.

최근 100회 × 전략당 3만 세트 결과, **모든 전략의 5등 적중률이 이론값 2.24%와 구별되지 않았다**
(비인기 2.35% / 빈도 2.33% / 균등 2.29%). 이건 실패가 아니라 설계대로다 —
확률은 손대지 않았고 배당만 건드렸다. 30만 세트에서 1·2등은 한 번도 나오지 않았다(기대값 각 0.13건, 0.02건).

## 6. 구조

```
scripts/fetch_draws.py    수집   동행복권 → site/data/draws.json (당첨번호 + 1~3등 당첨자수 + 판매액)
scripts/test_draws.py     검증   공식 통계 API와 번호별 출현횟수 대조
scripts/independence.py   검정   예측 가능성 7종 → site/data/independence.json
scripts/update.mjs        기록   추천 채점 + 다음 회차 추천 생성 (멱등)
scripts/test_analysis.mjs 검증   통계·인기지수·추천·채점 로직
scripts/backtest.mjs      측정   전략별 적중률 (배포에는 안 쓰임)

site/analysis.js          도메인 순수 함수만. DOM·fetch·전역 상태 없음
site/app.js               표현   analysis.js 결과를 그리기만 함
site/index.html, style.css
site/data/*.json          데이터 계약. 이 JSON이 모듈 간 유일한 인터페이스
```

**경계가 어디에 있고 왜 거기인가**

* **수집 ↔ 분석**: `draws.json`이 유일한 접점. 수집기는 동행복권 응답 스키마(`tm1WnNo`, `rnk2WnNope` …)를
  `{e, d, n[], b, w1, w2, w3, sales}`로 좁혀서 내보내고, 그 바깥으로 원본 스키마가 새지 않는다.
  동행복권이 API를 또 바꿔도 `slim()` 한 함수만 고치면 된다 (구 `common.do` API는 이미 폐지됐다).
* **도메인 ↔ 표현**: `analysis.js`는 입력을 받아 값을 반환할 뿐 DOM도 네트워크도 모른다.
  그래서 브라우저와 Node(`update.mjs`, 테스트, 백테스트)에서 **같은 코드가 그대로** 돈다 —
  화면에 보이는 인기지수와 채점에 쓰이는 인기지수가 갈라질 수 없다.
* **기록 ↔ 표현**: `predictions.json`은 추가만 하는 로그. `update.mjs`만 쓰고, 사이트는 읽기만 한다.

지금은 정적 파일이지만 경계가 JSON 계약에 있어서, 나중에 API 서버가 필요해지면
`site/data/*.json`을 같은 모양의 HTTP 엔드포인트로 바꾸는 것만으로 분리된다.
DB도 프레임워크도 없다 — 1,240행에 그게 필요해지면 그때 붙인다. BigQuery도 같은 이유로 쓰지 않는다.

## 7. 로컬 실행

```bash
python3 scripts/fetch_draws.py    # 전 회차 수집 (약 2분)
python3 scripts/test_draws.py     # 공식 통계와 대조
python3 scripts/independence.py   # 예측 가능성 검정 (약 5초)
node scripts/test_analysis.mjs    # 도메인 로직 검증
node scripts/update.mjs           # 채점 + 다음 회차 추천
python3 -m http.server 8000 -d site
```

의존성 없음. Python 3와 Node 18+ 표준 라이브러리만 쓴다.

## 8. 배포

Google Cloud Storage 정적 호스팅. GitHub Actions가 매주 일요일 새벽(KST)
수집 → 검증 → 검정 → 채점 → 커밋 → 배포한다.

인증은 Workload Identity Federation을 쓴다(서비스 계정 키 파일을 저장소나 시크릿에 두지 않는다).
저장소 시크릿 3개가 필요하다 — 값은 저장소에 커밋하지 않는다:

| 시크릿 | 내용 |
| --- | --- |
| `GCP_WIF_PROVIDER` | Workload Identity Provider 리소스 경로 |
| `GCP_SA_EMAIL` | 배포용 서비스 계정 이메일 |
| `GCS_BUCKET` | 배포 대상 버킷 이름 |
