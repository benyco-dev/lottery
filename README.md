# 로또 6/45 예상번호

동행복권 로또 6/45 전 회차 1등 당첨번호에서 **연관성을 뽑아 다음 회차 예상번호 6자리 5세트**를 만드는 정적 사이트.
예상번호는 추첨 전에 기록되고, 추첨 후 자동으로 채점된다.

> 로또는 매 회차 독립시행이라 어떤 조합이든 1등 확률은 8,145,060분의 1로 같습니다. 재미로만 보세요.

## 모델

과거 1등 번호에서 네 가지 연관성을 뽑는다. 전부 **리프트**(관측 ÷ 기대) 형태라 1.0 이 기준선이다.

| 요소 | 내용 | 가중 |
| --- | --- | ---: |
| 최근 빈도 | 반감기 300회로 가중한 출현 빈도 | 1.0 |
| 미출현 기간 | 마지막 출현 이후 회차 수 ÷ 기대 간격 7.5 | 0.6 |
| 직전 회차 전이 | 직전 회차 번호 다음 회차에 나온 번호 | 0.8 |
| 동반출현 | 이미 고른 번호와 같은 회차에 나온 빈도 | 1.4 |

각 요소를 z점수로 맞춰 더한 뒤 `exp(0.35 × 점수)` 로 가중 추출한다.
번호를 **하나씩 여섯 번** 뽑되, 뽑을 때마다 이미 고른 번호와의 동반출현 리프트를 다시 계산해 더한다.
그래서 한 세트 안의 6개가 서로 연관된 조합이 된다.

마지막으로 구조 필터를 통과한 조합만 남긴다 — 번호합이 과거 80% 구간 안, 홀수 2~4개,
연속쌍 1쌍 이하, 10단위 구간 3개 이상 분산.

가중치는 `site/analysis.js` 의 `MODEL` 상수 하나에 모여 있다. 바꿔서 돌려보면 된다.

## 예상번호와 채점

매 회차 5세트를 만든다. 시드가 대상 회차 번호라 같은 코드로 누구나 같은 결과를 재현할 수 있고,
예상번호는 추첨 **전에** `site/data/predictions.json` 에 커밋된다. 추첨 후 성적을 고쳐 쓸 수 없다.
과거 회차를 소급해서 기록에 넣지 않는다 — 기록은 앞으로만 쌓인다.

추첨 결과가 나오면 다음 실행에서 자동 채점한다. 1~3등이면 메인 상단에 당첨으로 표시하고,
낙첨이면 세트별로 몇 개 맞았는지 보여준다. 6개=1등, 5개+보너스=2등, 5개=3등, 4개=4등, 3개=5등.

모델은 **전체 이력**으로만 계산한다. 통계 탭의 5개 구간(전체 / 500 / 250 / 100 / 50회)은 관측용이다.

## 백테스트

`node scripts/backtest.mjs [회차수] [시드수]` — 과거 회차를 그 시점 데이터만으로 예상하고 채점한다.

최근 100회 × 전략당 2만 세트:

| 전략 | 평균 일치 | 5등 | 4등 | 5등 이상 |
| --- | ---: | ---: | ---: | ---: |
| 연관성 모델 | 0.798 | 481 | 29 | 2.55% |
| 균등 대조군 | 0.807 | 454 | 23 | 2.38% |
| *이론값* | *0.800* | *448.8* | *27.3* | *2.38%* |

모델과 대조군의 차이는 표본 오차 범위 안이다. 4만 세트에서 1·2·3등은 나오지 않았다(기대값 각 0.005 / 0.03 / 1.1건).

## 구조

```
scripts/fetch_draws.py    수집   동행복권 → site/data/draws.json
scripts/test_draws.py     검증   공식 통계 API와 번호별 출현횟수 대조
scripts/update.mjs        기록   예상번호 채점 + 다음 회차 생성 (멱등)
scripts/test_analysis.mjs 검증   통계·연관성·예상번호·채점 로직
scripts/backtest.mjs      측정   모델 성적 (배포에는 안 쓰임)

site/analysis.js          도메인 순수 함수만. DOM·fetch·전역 상태 없음
site/app.js               표현   analysis.js 결과를 그리기만 함
site/index.html, style.css
site/data/*.json          데이터 계약. 이 JSON이 모듈 간 유일한 인터페이스
```

**경계가 어디에 있고 왜 거기인가**

* **수집 ↔ 분석**: `draws.json` 이 유일한 접점. 수집기가 동행복권 응답 스키마(`tm1WnNo`, `rnk1WnNope` …)를
  `{e, d, n[], b, w1, w2, w3, sales}` 로 좁혀서 내보내고, 그 바깥으로 원본 스키마가 새지 않는다.
  동행복권이 API를 또 바꿔도 `slim()` 한 함수만 고치면 된다 (구 `common.do` API는 이미 폐지됐다).
* **도메인 ↔ 표현**: `analysis.js` 는 입력을 받아 값을 반환할 뿐 DOM 도 네트워크도 모른다.
  그래서 브라우저와 Node(`update.mjs`, 테스트, 백테스트)에서 **같은 코드가 그대로** 돈다 —
  화면에 보이는 리프트와 예상번호 생성에 쓰이는 리프트가 갈라질 수 없다.
* **기록 ↔ 표현**: `predictions.json` 은 추가만 하는 로그. `update.mjs` 만 쓰고, 사이트는 읽기만 한다.

지금은 정적 파일이지만 경계가 JSON 계약에 있어서, 나중에 API 서버가 필요해지면
`site/data/*.json` 을 같은 모양의 HTTP 엔드포인트로 바꾸는 것만으로 분리된다.
DB 도 프레임워크도 없다 — 1,240행에 그게 필요해지면 그때 붙인다.

## 로컬 실행

```bash
python3 scripts/fetch_draws.py    # 전 회차 수집 (약 2분)
python3 scripts/test_draws.py     # 공식 통계와 대조
node scripts/test_analysis.mjs    # 도메인 로직 검증
node scripts/update.mjs           # 채점 + 다음 회차 예상번호
python3 -m http.server 8000 -d site
```

의존성 없음. Python 3 와 Node 18+ 표준 라이브러리만 쓴다.

## 배포

Google Cloud Storage 정적 호스팅. GitHub Actions 가 매주 일요일 새벽(KST)
수집 → 검증 → 채점 → 커밋 → 배포한다.

인증은 Workload Identity Federation 을 쓴다(서비스 계정 키 파일을 저장소나 시크릿에 두지 않는다).
저장소 시크릿 3개가 필요하다 — 값은 저장소에 커밋하지 않는다:

| 시크릿 | 내용 |
| --- | --- |
| `GCP_WIF_PROVIDER` | Workload Identity Provider 리소스 경로 |
| `GCP_SA_EMAIL` | 배포용 서비스 계정 이메일 |
| `GCS_BUCKET` | 배포 대상 버킷 이름 |
