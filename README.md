# 로또 6/45 회차 통계

동행복권 로또 6/45의 1회차부터 최신 회차까지 당첨번호를 모아 5개 구간으로 나눠 분석하고,
과거 분포를 닮은 번호 조합 5세트를 회차마다 기록해 추첨 후 자동으로 채점하는 정적 사이트.

> **로또는 매 회차 독립시행입니다.** 과거 번호로 다음 번호를 맞힐 수 없습니다.
> 여기서 뽑는 조합은 예측이 아니라 *과거 당첨 조합의 분포와 닮은 무작위 조합*이고,
> 어떤 조합이든 1등 확률은 8,145,060분의 1로 같습니다. 재미로만 보세요.

## 분석 구간

전체 · 최근 500회 · 최근 250회 · 최근 100회 · 최근 50회.
구간마다 번호별 출현 횟수와 기대치 대비 편차, 핫/콜드/미출현 번호, 10단위 구간 분포,
세트당 홀수 개수 분포, 번호합 통계, 연속번호 등장률을 낸다.

## 예측과 채점

매 회차 5세트를 만든다 — **분석 구간 5개에서 각각 한 세트씩**.
난수 시드가 대상 회차 번호에 묶여 있어(`seed = 회차 × 10 + 구간index`) 같은 코드로 누구나 같은 결과를 재현할 수 있고,
예측은 추첨 **전에** `site/data/predictions.json`에 커밋된다. 추첨 후 성적을 고쳐 쓸 수 없다.

추첨 결과가 나오면 다음 실행에서 자동 채점한다. 1~3등이면 메인 화면 상단에 당첨으로 표시되고,
낙첨이면 세트별로 몇 개 맞았는지 보여준다. 등수 규칙은 6개=1등, 5개+보너스=2등, 5개=3등, 4개=4등, 3개=5등.

과거 회차를 소급해서 예측 기록에 넣지 않는다(백테스트는 실적이 아니다). 기록은 앞으로만 쌓인다.

## 백테스트

`node scripts/backtest.mjs [회차수] [시드수]` — 과거 회차를 그 시점 데이터만으로 되돌려 예측하고 채점한다.
구간별 성적을 이론 기대값, 그리고 빈도 가중 없이 뽑은 **균등 대조군**과 나란히 찍는다.

최근 100회(1141~1240) × 구간당 5만 세트로 돌린 결과, 다섯 구간 모두 5등 적중률이 2.25~2.36%로
이론값 2.24%와 구별되지 않았고 균등 대조군(2.50%)에도 앞서지 못했다. **빈도 가중은 효과가 없다.**
독립 표본이 회차 100개뿐이라 구간 간 우열을 가릴 만한 정밀도 자체가 나오지 않는다는 점도 같이 봐야 한다.

## 구조

```
scripts/fetch_draws.py    수집   동행복권 → site/data/draws.json
scripts/test_draws.py     검증   공식 통계 API와 번호별 출현횟수 대조
scripts/update.mjs        기록   예측 채점 + 다음 회차 예측 생성 (멱등)
scripts/backtest.mjs      검증   과거 회차로 구간별 성적 측정 (배포에는 안 쓰임)
scripts/test_analysis.mjs 검증   통계·추천·채점 로직

site/analysis.js          도메인 순수 함수만. DOM·fetch·전역 상태 없음
site/app.js               표현   analysis.js 결과를 그리기만 함
site/index.html, style.css
site/data/*.json          데이터 계약. 이 JSON이 모듈 간 유일한 인터페이스
```

**경계가 어디에 있고 왜 거기인가**

- **수집 ↔ 분석**: `draws.json`이 유일한 접점. 수집기는 동행복권 응답 스키마(`tm1WnNo`, `rnk1WnAmt` …)를
  `{e, d, n[], b}`로 좁혀서 내보내고, 그 바깥으로 원본 스키마가 새지 않는다.
  동행복권이 API를 또 바꿔도 `slim()` 한 함수만 고치면 된다 (실제로 구 `common.do` API는 이미 폐지됐다).
- **도메인 ↔ 표현**: `analysis.js`는 입력을 받아 값을 반환할 뿐 DOM도 네트워크도 모른다.
  그래서 브라우저와 Node(`update.mjs`, 테스트)에서 **같은 코드가 그대로** 돈다 —
  화면에 보이는 통계와 채점에 쓰이는 통계가 갈라질 수 없다.
- **기록 ↔ 표현**: `predictions.json`은 추가만 하는 로그. `update.mjs`만 쓰고, 사이트는 읽기만 한다.

지금은 정적 파일이지만 경계가 JSON 계약에 있어서, 나중에 API 서버가 필요해지면
`site/data/*.json`을 같은 모양의 HTTP 엔드포인트로 바꾸는 것만으로 분리된다. DB도 프레임워크도 아직 없다 —
1,240행짜리 데이터에 그게 필요해지면 그때 붙인다.

## 로컬 실행

```bash
python3 scripts/fetch_draws.py   # 전 회차 수집 (약 2분)
python3 scripts/test_draws.py    # 공식 통계와 대조
node scripts/test_analysis.mjs   # 도메인 로직 검증
node scripts/update.mjs          # 채점 + 다음 회차 예측
python3 -m http.server 8000 -d site
```

의존성 없음. Python 3와 Node 18+ 표준 라이브러리만 쓴다.

## 배포

Google Cloud Storage 정적 호스팅. GitHub Actions가 매주 일요일 새벽(KST) 수집 → 검증 → 채점 → 커밋 → 배포한다.

인증은 Workload Identity Federation을 쓴다(서비스 계정 키 파일을 저장소나 시크릿에 두지 않는다).
저장소 시크릿 3개가 필요하다 — 값은 저장소에 커밋하지 않는다:

| 시크릿 | 내용 |
| --- | --- |
| `GCP_WIF_PROVIDER` | Workload Identity Provider 리소스 경로 |
| `GCP_SA_EMAIL` | 배포용 서비스 계정 이메일 |
| `GCS_BUCKET` | 배포 대상 버킷 이름 |
